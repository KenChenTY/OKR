# Windows Server 部署运行说明

## 发布前置条件

准备企业批准的Windows Server、Nginx for Windows、Python 3.12、ODBC Driver 18、SQL Server、TLS证书、Entra应用及扫描服务。当前仓库尚未连接企业基础设施，不能将构建成功视为已经通过生产上线验收。

应用和数据库建议分机。用户仅访问Nginx的443，API仅监听127.0.0.1:8000；SQL Server端口仅对指定应用和管理节点开放。Nginx Windows版的worker及连接能力需要在实际服务器压测，不能套用Linux吞吐假设。

## 发布步骤

1. 在构建环境安装锁定依赖、运行后端测试、前端构建及依赖审计，生成版本化包。
2. 在 `D:\OKR\releases\<版本>` 放置代码和 `frontend\dist`，为该版本创建独立虚拟环境并安装后端锁文件。
3. 创建运行服务账号、日志、临时目录、隔离区、证据区和导出区；证据及导出不在Nginx静态root内。
4. 配置环境变量或受ACL保护的backend/.env。必须 `OKR_ENV=production`、`OKR_AUTH_MODE=entra`、`OKR_ENABLE_DEV_LOGIN=false`，填写真实HTTPS公共地址、身份参数、存储绝对路径及可信SQL连接。
5. 备份数据库，由迁移身份执行 `alembic upgrade head`；由DBA按 `deploy/sql/runtime-role.sql` 创建运行角色并授权专用账号。管理初始化使用不同身份。
6. 复制并修改 `deploy/nginx/nginx.conf`，替换域名、证书、版本目录。将Nginx发行包的mime.types保留在conf目录，创建logs及temp/client_body、temp/proxy。
7. 使用企业批准的服务包装器托管Nginx、API及Worker。仓库提供WinSW风格XML样例，需要按批准的包装器版本验证其配置格式并设置专用低权限服务身份；不使用默认LocalSystem运行。
8. 配置测试通过后重载Nginx，启动API及Worker。验证探针、真实SSO、两级审批、上传扫描、下载权限、导出和审计，再开放业务访问。

Nginx账号只读静态资源、配置及私钥，可写自己的日志和temp。API/Worker账号按功能授权存储目录。日志不记录OIDC查询参数；保留API错误追踪ID，禁止打印密钥及连接串。

## 扫描器约定

`OKR_SCANNER_EXECUTABLE` 为本地受控程序或包装脚本的可执行文件绝对路径。Worker以参数数组调用 `scanner <文件绝对路径>`，不使用shell拼接。退出码0表示干净，1表示感染并拒绝，其他退出码或超过120秒作为扫描服务异常重试，期间文件保持隔离。应将企业扫描工具具体的返回码和“引擎不可用”状态映射到此约定。

未配置扫描器或任务异常，文件保持PendingScan；不会绕过检查。三次失败后进入Failed队列，需要运维检查后显式重放。仅支持xlsx、pptx、pdf、png及jpeg；xls、ppt和宏格式在扫描能力确认前不开放。

隔离文件扫描通过后复制到证据区，保留隔离副本用于失败恢复。隔离区清理和文件保留期暂由运维策略管理，清理前核对数据库引用、备份和保留锁，不直接按目录日期删除。

## 监控与故障处理

- `/health/live`：进程存活；`/health/ready`：数据库迁移版本与存储可写。公共登录页使用 `/api/status` 获得不包含内部配置的就绪状态。
- API数据库连接登录超时5秒，语句超时30秒。异常返回503及追踪ID，具体连接问题在运维侧检查。
- Worker每分钟调度提醒和每日目标快照，任务用事务锁和5分钟租约领取。快照任务过期不会将今日值伪装成历史数据。
- 站内提醒已实现；Teams、邮件及外部项目连接器属于后续集成，不会自动向外发送消息。
- 导出限制为2000个目标及最多3个待处理任务；按当前用户权限执行，下载时重新逐个核验目标权限，文件有效期24小时。
- 查询jobs表定位Failed任务，修正外部依赖后由受控运维流程将状态重置为Pending并记录操作。系统管理员可在任务运维页执行有审计的重放；没有无鉴权重放接口。
- 日志轮转后执行Nginx `-s reopen`，通过 `reload-nginx.ps1` 检查配置后重载；命令必须使用服务同一身份及prefix。

## 备份与回滚

数据库建议每周全量、每日差异、每15分钟日志备份，需由DBA确认恢复模式与日志链。证据、配置和必要密钥同时纳入受控异机备份。恢复时以数据库引用版本逐项核验文件及SHA-256，不能只验证数据库可启动。

当前迁移采用追加模式，初始及治理迁移拒绝破坏性downgrade。应用回滚要求数据库仍兼容；破坏性调整须以经过演练的备份恢复计划执行。正式上线前必须完成SQL Server事务和并发测试、Entra/MFA验证、病毒扫描验证、Nginx容量压测及恢复演练。
